## 为什么 wiki 就是真相

大多数"AI 记忆"工具,都把你的记忆锁进一个你看不见的东西里——一个向量库,一个看不透的索引。OMem 偏要反着来,这一注借自 Andrej Karpathy 那个 **LLM 读得懂的 wiki** 的想法:核心产物就是一份人能读的 Markdown wiki,而它*本身*就是检索语料。agent 读的和你读的,是同一份东西。

这带来一个看得见摸得着的好处。索引都只是叠在上头的看法——全删了,它们能从 wiki 重建。wiki 本身又是从那份不可变的 `raw/` 归档生成的——wiki 删了,它能从 `raw/` 重建。没有一样东西被关起来:备份、版本控制、手动改一页、换台机器接着用,随你。你的工作上下文还是你的,而且是一种五十年后还打得开的格式。

## 为什么解析是确定性的

一个挺在理的问题:前沿 LLM 直接读个 PDF、读个 PPT 都不在话下——那 OMem 干嘛还要跑 python-pptx、pymupdf、再加个视觉模型,费劲做出一份 `parsed.md`,而不是把文件往 LLM 手里一塞了事?

因为 OMem 是一份**归档**,而归档讲究的是 *Stable-A*:同样的输入,今天和三年后,都能重建出一模一样、连字节都不差的结果。这个保证,只有确定性的函数给得了。LLM 解析器给你的是 *Stable-B*——写下那一刻是冻住了,可它不可复现:模型一退役,或者采样一漂,你就再也拿不回当初那份 `parsed.md` 了。把确定性这条链换成 LLM,会神不知鬼不觉地把归档毁掉(顺带连整理缓存、连"拿一次 prompt 改动去 diff 一份固定解析"的能力一起毁掉)。它还会悄悄把那些不那么规整的文字抹平:一个怪具体的数字,比方 `11.3%`,到它手里可能就被圆成了 `11%`;而 python-docx 还你的,是文件里一字不差的原文。

所以默认这条链就一直是确定性的。一个 `parser-llm` 插件留给了 v1.5,给那些把视觉、版面理解看得比归档保真更重的人——这是个实打实的取舍,明明白白摆出来让你自己挑,而不是默认替你拿了主意。

<Aside type="note" title="对 v1.0 说实话">
这些原则勾的是系统的骨架,不是一条已经走到头的边界。顺着它们往下,自然会引出几样东西:按实体抽取的 wiki(每个人、每个项目各一页)、完全离线运行、跨设备同步——可这些都被有意 [划在了 v1.0 的范围之外](/zh-cn/concepts/01-what-is-omem/#现在就能用)。原则照样立得住;铺得到多大的面,v1.5 之后再慢慢长。
</Aside>
